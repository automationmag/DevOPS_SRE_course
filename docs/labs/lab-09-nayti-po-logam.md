# Лаборатория 9. Найти причину только по логам

**Цель:** намеренно сломать один слой, найти причину по логам и статусу контейнеров, починить и записать разбор.

**Время:** 30–45 минут.

**Нагрузка:** влезает в 1 ГБ. «Пульс» должен работать.

!!! danger "Что ломать нельзя"
    Не трогайте в этой лаборатории SSH и файрвол — слишком легко отрезать себя от сервера. Ломаем только приложение.

## Шаг 1. Запомнить, как выглядит норма

**Зачем:** чтобы узнать отклонение, надо сначала увидеть нормальное состояние. Этот шаг пропускают чаще всего и потом не понимают, что в логе не так.

**Где вводить:** терминал сервера (`ssh ucheb`)

```bash
cd /opt/pulse
docker compose -f compose.caddy.yml ps
docker compose -f compose.caddy.yml logs pulse --tail=20 --timestamps
```

**Что должно получиться:**

- оба контейнера в состоянии `Up`;
- в логе строка о прослушивании порта и записи о запросах.

Запишите, как это выглядит. Через пять минут будет с чем сравнить.

## Шаг 2. Поставить свою метку в лог

**Зачем:** научиться находить конкретный запрос среди множества строк.

**Где вводить:** терминал сервера

```bash
curl -s -H "X-Request-Id: lab9-ok" http://127.0.0.1:8080/health
docker compose -f compose.caddy.yml logs pulse --tail=20 | grep lab9-ok
```

Если порт 8080 закрыт после модуля 5, используйте свой адрес:

```bash
curl -s -H "X-Request-Id: lab9-ok" https://pulse.ваш-домен.ru/health
docker compose -f compose.caddy.yml logs pulse --tail=20 | grep lab9-ok
```

**Что должно получиться:** строка с меткой `lab9-ok`. Это ваш собственный запрос, найденный в логе.

## Шаг 3. Сломать слой «процесс»

**Зачем:** самый простой вид отказа. Учимся узнавать его по признакам, а не по догадкам.

**Где вводить:** терминал сервера

```bash
docker compose -f compose.caddy.yml stop pulse
```

Теперь проведите разбор **не заглядывая в ответ**. Пройдите по шагам:

```bash
docker compose -f compose.caddy.yml ps
```

**Что должно получиться:** у `pulse` состояние `Exited`, у `caddy` — по-прежнему `Up`.

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://pulse.ваш-домен.ru/health
```

**Что должно получиться:** код `502`. Читается так: вахтёр работает, а тот, к кому он обращается, не отвечает.

```bash
docker compose -f compose.caddy.yml logs caddy --tail=20
```

**Что должно получиться:** строка о неудачной попытке соединиться с `pulse`.

**Вывод, который надо записать:** слой «процесс приложения», контейнер остановлен, вахтёр при этом исправен.

Возвращаем:

```bash
docker compose -f compose.caddy.yml start pulse
```

## Шаг 4. Сломать слой «права на данные»

**Зачем:** более коварный отказ. Сайт при этом открывается, и по внешнему виду проблема не очевидна.

**Где вводить:** терминал сервера

```bash
cd /opt/pulse
sudo chown -R root:root data
sudo chmod 000 data
docker compose -f compose.caddy.yml restart pulse
```

Откройте сайт в браузере и попробуйте сохранить заметку.

**Что должно получиться:** страница открывается, но заметка не сохраняется либо появляется ошибка.

Ищем причину:

```bash
docker compose -f compose.caddy.yml ps
docker compose -f compose.caddy.yml logs pulse --tail=40
```

**Что должно получиться:**

- состояние `Up` — процесс жив, то есть слой «процесс» исправен;
- в логе строка со словами `Permission denied` и путём `/data`.

**Вывод:** слой «доступ к данным», у приложения нет прав на папку.

Обратите внимание на разницу с шагом 3: там процесс лежал, здесь работает. Один и тот же симптом «сайт не работает» имеет разные причины, и логи их различают.

## Шаг 5. Починить

**Где вводить:** терминал сервера

```bash
sudo chmod 755 /opt/pulse/data
sudo chown -R 10001:10001 /opt/pulse/data
docker compose -f compose.caddy.yml restart pulse
ls -la /opt/pulse/data
```

**Что должно получиться:** владелец папки — `10001`, права `drwxr-xr-x`.

Проверяем результат:

```bash
curl -s https://pulse.ваш-домен.ru/health
```

**Что должно получиться:** `{"status":"ok"}`. В браузере заметка снова сохраняется.

## Шаг 6. Записать разбор

**Зачем:** это заготовка описания инцидента из модуля 12. Тренируемся на учебной поломке.

Заполните пять строк по каждой из двух поломок:

1. Что видел человек: текст ошибки или описание поведения.
2. Отвечал ли SSH: да.
3. Что показывал `docker compose ps`.
4. Ключевая строка из логов.
5. Вывод: какой слой был сломан и чем лечилось.

**Что должно получиться:** два коротких разбора по пять строк. Сравните их — при похожем внешнем симптоме содержание разное.

## Если что-то пошло не так

| Симптом | Причина | Что делать |
|---|---|---|
| после `chmod 000` пропал доступ к логам | права сняты слишком широко | выполните шаг 5, права восстановятся |
| `curl` не отвечает вовсе, а не 502 | остановлен не тот контейнер | `docker compose ps`, запустите `caddy` |
| метка `lab9-ok` не находится | приложение не логирует заголовок | посмотрите `--tail=50` без `grep` |
| заметка не сохраняется после починки | контейнер не перезапущен | `docker compose restart pulse` |

## Готово, если

- [ ] Нашли свою метку в логе
- [ ] Различили два отказа: остановленный процесс и нехватку прав
- [ ] Назвали каждый слой словами, а не догадками
- [ ] Починили командами, не переустанавливая систему
- [ ] Записали два разбора по пять строк
- [ ] Связали ощущения с [карточкой «сайт не открывается»](../runbooks/site-down.md)
